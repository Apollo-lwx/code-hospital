# code-hospital git worktree 高危隔离设计草案

> 定位：open-decisions 挂账的「git worktree——仍是高危可选增强，不是当前施治路径」、
> 路线图 P3「git worktree 高危隔离」的专项设计。回答四个问题：隔离间放哪、
> 怎么施治、怎么合回、什么药进隔离间。本草案只定设计，拍板后才动代码。
>
> 一句话主张：**高危药方先进隔离间预演，验收过了才合回主仓；
> 失败就删掉隔离间，主仓一根汗毛不伤。**

---

## 0. 为什么需要它（现状的真实风险）

现状施治直接写主仓工作区。快照 + 字节级回滚能兜住「验收失败」，
但兜不住两件事：

1. **过程态污染**：多文件重写（大范围正骨、跨文件修复）施治到一半，
   主仓工作区就是破的——用户这时候想切分支、想临时跑个东西，都被绑架；
2. **灾难半径**：医院进程崩溃、机器断电发生在「写完未验收」的窗口里，
   主仓留一地半成品，靠人对着快照收拾。

隔离间把这两件事的爆炸半径收进一个可随时删除的目录。

## 1. 隔离间模型

- **位置**：`.hospital/worktrees/<item_id>/`。病房的隔离间归医院自己管，
  `.hospital/` 已在 `.git/info/exclude`，主仓 `git status` 永远看不见它。
- **身份**：`git worktree add --detach <path> <base_commit>`——detached，
  不建分支、不污染用户的分支列表；base_commit 取挂号时记录的病例基线
  （scope.commit 或建档 HEAD）。医院对主仓的 git 操作**只有**
  `git worktree add / remove / prune` 三个——它们动的是 `.git/worktrees`
  元数据，不碰历史、不碰用户分支。
- **账不搬家**：病例库、报告、快照、剂量全部留在**主仓** `.hospital/`。
  隔离间只是文件操作的目标，不是另一家医院——platform-evolution §遗留
  记过「worktree 各算一套身份」的坑，本设计用「workspace root ≠
  hospital root」双 root 绕开：文件操作走隔离间路径，读写病历走主仓路径。
  记忆权重、查重、互斥锁全部仍在主仓身份下，一套也不多。
- **互斥不变**：一仓一病例、施治串行的既有锁照旧；同一病例同时最多一个
  隔离间。出院 / 转院时清扫名下隔离间（`git worktree remove --force` +
  `prune`），残留进覆盖账。

## 2. 施治流程（对比现状）

| 步 | 现状（直写主仓） | 隔离模式 |
|---|---|---|
| 取药/生成 | 同 | 同（patch/lsp 产出与落盘位置无关） |
| 四道校验 | 对主仓 before 校验 | 对**隔离间** before 校验（隔离间检出基线，等于主仓该文件最近已知状态） |
| 落盘 | 写主仓 | 写隔离间 |
| 验收 | 主仓跑 acceptance | **隔离间**跑 acceptance（环境布置见 §4） |
| 失败 | 快照恢复主仓 | **删隔离间，主仓零接触**——这是全部卖点 |
| 成功 | —（已在主仓） | **合回**（§3）+ 主仓复验 |

dry_run 语义不变（隔离间内推演不落盘……不，隔离间本身就是干跑间：
dry_run 在隔离模式下等价于「预演但不合回」）。

## 3. 合回策略（三选一，本草案拍 (c)）

- **(a) patch 回合**：隔离间里生成 diff，回主仓把同一份 patch 再过一遍
  四道校验管线。优雅（主仓写入路径唯一），但同一份药煎两遍，
  且两遍之间主仓可能漂移，第二遍的锚点可能挂——把「隔离间已验收」
  与「主仓要施治」变成两个事实，对账复杂。
- **(b) commit + cherry-pick/merge**：隔离间提交到临时分支再合回用户分支。
  **否决**：医院从此在用户仓里造提交、动历史——现行设计的一切（patch 只落
  工作区、回滚不动 git）都建立在「医院不碰 git 历史」上，这条不破。
- **(c) 文件复制回合（采）**：验收过后，把本味触及的文件从隔离间
  **逐文件复制**回主仓。前置闸：主仓这些文件的当前内容与施治前快照
  **逐字节一致**（drift 检查）——一致才复制；不一致说明用户在预演期间
  动过这些文件，走 `rollback_conflict` 同款挂起 + `resolve_conflict`
  续行（manual_resolved / retry / skip_item），隔离间现场保留供人工核对。
  复制后逐文件与隔离间版本字节级比对，缺一即 rollback_conflict。
- **合回后主仓复验**：同一内容同一命令为什么不直接在主仓信隔离间的
  验收？因为环境不完全等同（§4 的 junction 毕竟是链接不是本体）。
  主仓复验失败按**现有**验收失败路径走（快照恢复主仓）——注意此刻
  主仓快照就是合回前状态，恢复等于没合回过，闭环干净。
  成本：高危药方验收跑两遍。高危本来就走真人审批，成本可接受；
  二期按真实观察再议是否可配关掉。

## 4. 验收环境（隔离间最大的现实坑）

`git worktree add` 只检出**被跟踪**的文件——`.venv/`、`node_modules/`、
`target/` 这些被 ignore 的依赖目录在隔离间里**不存在**，验收命令直接残废。
对策是合回前在隔离间做「布置」：

- 把主仓的依赖目录以**链接**接入隔离间：POSIX 用 symlink，Windows 用
  directory junction（无需管理员权限）。内置默认清单：
  `.venv`、`venv`、`node_modules`；仓库可用 `code-hospital.yaml` 的
  `safety.worktree.link_dirs` 追加/覆盖（配置即代码，与处置矩阵同一精神）。
- 链接而非复制的理由：node_modules 量级复制不起；链接后测试写进依赖目录
  的缓存（__pycache__、.pytest_cache、turbo cache）落在主仓的忽略目录里，
  可接受——这些目录本来就是工具自己管理的易失品。
- 没有配置验收命令（acceptance 为空）时跳过布置，直接合回。
- **反例同样进草案**：验收命令若会写依赖清单文件（package-lock、
  requirements.txt 冻结）——那是被跟踪文件，写的就是隔离间副本，
  合回时若不在本味 scope 内会被 drift 检查拦下，行为正确。

## 5. 触发条件与配置

- `code-hospital.yaml` 新增 `safety.worktree: never | high | always`，
  默认 **`high`**：risk=high 的药味进隔离间；`never` 维持现状直写主仓；
  `always` 全量隔离。
- `hosp_dispense` 增入参 `isolation: bool | null`——null 走配置，
  显式 true/false 当次覆盖（自己的仓自己说了算）。
- 审批闸门对高危药方多一句提示：「本方高危，将/可进隔离间施治」，
  风险提前告知，与处置矩阵放宽时的 instructions 口径一致。
- 与处置矩阵的关系：worktree 是**执行环境**维度的加固，与
  class/auto_fix/confirm 正交，不进 dispositions 表，单独配置面。

## 6. 失败语义总表

| 失败点 | 行为 |
|---|---|
| 隔离间内校验/落盘失败 | 删隔离间，主仓零接触；剂量记 failed，原因照实 |
| 隔离间内验收失败 | 删隔离间，主仓零接触；按现有验收失败口径记 dose |
| 合回 drift 检查不过 | 主仓未动；隔离间现场保留，rollback_conflict 挂起走 resolve_conflict |
| 合回复制/比对失败 | 主仓已写部分按快照恢复（快照=合回前状态），挂起走续行 |
| 主仓复验失败 | 快照恢复主仓（等于没合回过），隔离间保留一轮供核对后清扫 |
| 医院进程崩溃 | 主仓无半成品（最坏情况是隔离间残留，下次挂号/出院清扫 + 台账） |

## 7. 明确不做

- 不在用户仓造提交、建分支、动 git 历史（`worktree add/remove/prune` 除外）；
- 不做并发多隔离间（一病例一间，施治串行不变）；
- 不隔离挂号/检验/诊断——隔离只管施治落盘这一段；
- 不替用户处理主仓既有脏状态：主仓对本味文件有未提交改动时，drift 检查
  自然会拦，医院不预先 stash；
- 与移动剂型正交：两个特性不互相依赖，谁先落地都行。

## 8. 分期与验收断言

- **一期**：`high` 档（高危进隔离间）+ `never/high/always` 配置 + junction
  布置 + 合回 drift 检查与主仓复验；python/ts 真实仓观察。
- **二期**：按观察再议——复验可否按规则类配置关闭、link_dirs 默认清单
  扩充、always 档的性能账。

| 断言 | 含义 |
|---|---|
| 现状可关 | `never` 时行为与现状逐字节一致 |
| 零接触 | 隔离间内任何失败，主仓工作区与 git 状态逐字节不变 |
| 身份不裂 | 病例库/报告/快照/记忆权重全在主仓 .hospital，无第二身份 |
| 漂移拦截 | 预演期间主仓被碰过的本味文件，合回必拦、必走 resolve_conflict |
| 合回一致 | 合回后逐文件字节级比对；主仓复验失败即快照恢复 |
| 现场不丢 | 合回冲突时隔离间保留供人工核对，清扫只在出院/续行决议后 |
| git 克制 | 主仓 git 操作只有 worktree add/remove/prune，历史与分支零变化 |

## 9. 开放问题

- `link_dirs` 内置默认清单（.venv/venv/node_modules）够不够——Java 的
  `target/`、`build/` 是产物不是依赖，不链；真实仓观察后定稿；
- 双验收（隔离间 + 主仓复验）的成本观察，二期决定是否可配；
- 隔离间检出 base_commit 与主仓当前 HEAD 分叉过大时（用户预演期间提交了
  新 commit 且触及本味文件）——drift 检查能拦住文件级冲突，但「基线过时」
  要不要单独提示，按真实使用再议。

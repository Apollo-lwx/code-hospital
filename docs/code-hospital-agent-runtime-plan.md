# 代码医院 · 向 Agent Runtime 演进的改进方案

> 版本：v1（2026-10-28）｜上位文档：
> [`code-hospital-design.md`](./code-hospital-design.md)（设计契约）、
> [`code-hospital-roadmap.md`](./code-hospital-roadmap.md)（能力路线）、
> [`code-hospital-open-decisions.md`](./code-hospital-open-decisions.md)（未决事项）。
>
> 本文件只管**架构与运行时**的演进，不管"新增哪些检查规则/仪器"（那是 roadmap 的事）。
> 每个阶段可独立交付、独立回退，阶段之间保持向后兼容。

## 0. 结论摘要

代码医院现在不是工具型 MCP，而是 **Workflow-as-a-Tool**：把一条六阶段、带人在环门禁、
带持久化病历的流水线封装成 8 个 `hosp_*` 工具，状态放在服务端而不靠宿主上下文记忆。

它**已经是一个编排型 Agent 的确定性内核**，缺的不是"智能"，是三样东西：

1. 门禁靠约定而非协议（R1，最致命）
2. 执行方只能点名不能执行（R4）
3. 没有疗效闭环，证明不了自己治好了病（R5）

演进方向：**A2（编排型 Agent Runtime）+ A3（双向可编排节点）**。
明确**不做** A1（自治 Agent：自调模型、自审批）——那会摧毁可审计、人在环、
不持有模型凭据三项核心资产。一句话：**骨架做硬、把手伸出，不给自己长大脑。**

## 1. 目标形态与边界

### 1.1 要做成什么

| 维度 | 现在 | 目标 |
|---|---|---|
| 对外身份 | 一个 MCP Server，8 个工具 | 仍是 MCP Server，但内部是显式 Runtime（状态机 + 作业 + 执行方） |
| LLM 位置 | 宿主自带，医院只出任务单 | 不变；但交卷变成**结构化契约**，可校验、可计数 |
| 门禁 | 返回值文本 + SKILL 纪律（约定级） | 协议级（elicitation），不支持时降级并显式标记 |
| 外部能力 | 只登记 PATH 是否存在 | 真正可调用，产物进覆盖账 |
| 结论可信度 | 不区分来源 | 每条结论带来源标记，可差分与不可差分分开 |

### 1.2 明确不做

- **不让医院自己调模型、不持有任何模型凭据。** 需要模型判断的环节始终由宿主完成。
- **不做自治审批。** 高危项永远要真人确认，任何"自动放行高危"的口子都不开。
- **不新增 `hosp_*` 工具**（沿用设计 §2 的纪律：能力挂进现有流程，守住工具数量）。
- **不在本阶段引入多租户与并发**（见 §2 约束）。

## 2. 三条已确认的约束

| # | 约束 | 对方案的影响 |
|---|---|---|
| C1 | 医院进程不持有模型凭据，模型能力由宿主提供 | A1 出局；`hosp_treat` 停在 `need_patch` 是固有边界，不是待修缺陷 |
| C2 | 先个人本地、后平滑上团队 | 并发/租户/异步作业**不修**，但架构要预留（锁与 treat 循环抽象成接口） |
| C3 | 不对模型部署位置设限 | 方案与文档中不讨论部署位置相关话题 |

## 3. 现状风险清单

按严重度排序，后续每个阶段的验收都直接对应其中一条或多条。

| 编号 | 风险 | 现状 | 后果 |
|---|---|---|---|
| **R1** | 门禁是软门禁 | `questions.py` 的 `channel="convention"`，靠 SKILL.md 纪律约束宿主 | 宿主擅自传 `stage_confirmed=true` 即三道闸全废，且**静默失效** |
| **R2** | 工具接口三义性 | 每个工具同时承担执行/确认/回流答案三种语义，布尔旋钮膨胀 | LLM 误用概率高，无法做权限细分 |
| **R3** | 单进程单仓 | 一仓一活跃病例，SQLite 单写者，`hosp_treat` 同步 12 步循环靠 timeout 挂起 | 上团队/CI 即崩（本阶段不修，只预留接口） |
| **R4** | 执行方只点名不执行 | `external` 只登记 PATH，`llm` 只出任务单 | 外聘仪器永远是摆设，能力层上不去 |
| **R5** | 无疗效闭环 | 处方疗效统计缺样本；SWRBench 功能召回 0.118 | 无法证明治好了病，也无法自动调优 |

## 4. 分阶段方案

### 阶段 0 · 地基：来源标记与能力探测

**目标**：在让模型深度参与之前，先把"这条结论是谁下的"记下来。这是后面一切的地基——
没有它，复诊差分会因 LLM 结论不可复现而失效。

**为什么先做这个**：它是四个阶段里改动最小、最不影响现有链路、但又不做就后面全废的一个。

#### 任务 0.1：结论来源标记

> ⚠️ **落地陷阱**：`findings` 表**已有一个 `origin` 列**，语义是"初发 / 医源性新症 / 无关新症"
> （`core/models.py` 的 `Origin` 枚举），与本任务要表达的"谁下的结论"完全不同。
> **必须另起字段名，建议 `concluded_by`，不要复用 `origin`。**

新增枚举与字段：

```
concluded_by: instrument | host_llm | external | code
  instrument  确定性仪器（ruff / semgrep / gitleaks / 内置尺子）—— 可复现，可差分
  external    外聘仪器产物                                    —— 视仪器而定
  code        医院内置的事实采集（catalog 中 executor=code）    —— 可复现
  host_llm    宿主模型交卷                                    —— 不可复现，不进疗效判定
```

改动点：

- [x] `core/models.py`：`Finding` 加 `concluded_by: str = "instrument"`；
      `Diagnosis` 加 `concluded_by: str = "code"`（模板归因=code）
- [x] `storage/db.py`：`_migrate()` 内加两列（`PRAGMA table_info` + `ALTER TABLE ... ADD COLUMN`，
      沿用现有幂等迁移写法）；补 INSERT 语句字段
- [x] `storage/reports.py`：检验报告与诊断书按 `concluded_by` 分组计数；
      覆盖账 `coverage_json` 增加 `concluded_by_counts`
- [x] `docs/code-hospital-io-contracts.md`：同步出参字段说明

**关键设计约束（必须遵守）**：

- 指纹差分（`db.find_fingerprint_history`、复诊疗效判定）**只统计 `concluded_by != host_llm` 的项**。
  LLM 结论不可复现，混进差分会让"复发×N"和疗效判定失真。
- `host_llm` 的发现默认标记为**待核实线索**，不参与 severity 排序的头部占位。

**验收**：一个含宿主交卷的病例，报告里能分别看到"仪器 N 条 / 模型 M 条"；
同一病例重扫两次，仪器部分差分一致，模型部分不计入疗效。

**已落地**：字段名用 `concluded_by`。`tool=host` 或 `rule_id=diff.issue` 写成 `host_llm`，引擎为 `external` 的仪器写成 `external`，其余仪器写成 `instrument`。诊断簇默认 `code`，整簇都是宿主交卷时写成 `host_llm`。存量库把已有的 `host` / `diff.issue` 回填成 `host_llm`。检验报告和诊断书写「仪器 N 条 / 模型 M 条」，宿主交卷单独成「待核实线索」，并排在严重度清单后面。覆盖账带 `concluded_by_counts`。指纹复发查询和出院差分只拿 instrument、external、code。

#### 任务 0.2：宿主能力探测与降级标记

**目标**：让"宿主支不支持某个协议能力"变成运行时可知、报告中可见，而不是靠猜。

改动点：

- [x] 新建 `api/capabilities.py`：从 `Context` 读 `client_capabilities` 与 `protocol_version`，
      导出 `supports_elicitation(ctx) -> bool`
- [x] `departments/*` 各阶段出口：不支持时仍走现有 `convention` 通道，
      但在返回里加 `degraded: true` 与 `degraded_reason`
- [x] 覆盖账记录本次会话的能力探测结果

**验收**：在不支持 elicitation 的宿主上跑一遍，报告覆盖账出现"门禁降级为约定级"字样；
支持时该行消失。**降级必须可见**——这是本任务唯一的硬性要求。

**已落地**：`supports_elicitation` 看 `client_capabilities.elicitation` 是否存在，并记下 `protocol_version`。各 `hosp_*` 入口绑定这次探测。科室出口在未声明 elicitation 时返回 `degraded: true` 与 `degraded_reason`（「门禁降级为约定级」），`channel` 仍是 `convention`。检验报告的覆盖与限制写上这一句，覆盖账写入 `host_capabilities`。宿主声明了 elicitation 时，出参不带降级字段，报告里也不写这一句。尚未绑定探测的直接调用保持原样。

### 阶段 1 · 门禁协议化（治 R1 / R2）

**目标**：把"靠 SKILL.md 纪律约束宿主"换成"协议约束 + 服务端强校验"。

#### 任务 1.1：elicitation 接入

> **已核实的 SDK 事实**（本机 venv `mcp==2.3.0`，`mcp.server.mcpserver`）：
> - `Context.elicit(message, schema) -> ElicitationResult[T]` 可用
> - 返回三态：`AcceptedElicitation{action:'accept', data}` /
>   `DeclinedElicitation{action:'decline'}` / `CancelledElicitation{action:'cancel'}`
> - `Context.client_capabilities`、`Context.protocol_version`、`Context.request_state` 可用
> - `create_message` / `request_sampling` **不存在**（sampling 已在 2026-07-28 版废弃，不要依赖）
>
> 三态正好对应门禁的"确认 / 暂停 / 取消"三条路，不需要自己造。

改动点：

- [x] `mcp_server.py`：给需要门禁的工具加 `ctx: Context | None = None` 参数
      （0.2 已给八个工具加上，并在调用前后 bind / reset）
- [x] `core/questions.py`：`ask()` 与 `stage_gate_question()` 仍是同步构造器。
      `present()` 在宿主声明了 elicitation 时调用 `ctx.elicit()`，否则原样交回
- [x] 门禁结果处理：`accept` 且选项不是 `pause` / `defer` → 同一次调用继续；
      `decline` / `cancel` / `pause` / `defer` → 挂起不执行
- [x] **保留降级路径**：elicitation 失败或 20 秒超时回退到 `convention` 并标 `degraded=true`

**风险与回退**：elicitation 依赖宿主实现度，各宿主参差不齐。
必须按**增强项**设计而非**依赖项**——失败时行为与今天完全一致。

**已落地**（2026-10-28）：`present()` / `release()` 读本次绑定的上下文。确认通过后检验、诊断、开方、施治、出院在同一次调用里往下走；暂停、拒绝、取消停在原地。`diff.issues` 和豁免理由走 elicit 的 `text`，空文本不执行。成功确认后覆盖账 `channel` 写成 `elicitation`；没问到人或问失败仍是 `convention`。确认参数算不算数见 1.2。

#### 任务 1.2：把 SKILL 纪律下沉为服务端强校验

不依赖宿主守约，改由医院自己拒绝：

- [x] `approver="user"` 时，`user_confirmed` 只认 elicitation 的 `accept` 回执，
      否则直接返回错误而不是静默放行
- [x] 高危处方项的自批路径（`approver="host_agent"`）在高危时一律拒绝
- [x] `stage_confirmed=true` 但当前 `pending_gate` 为空时，记录一次异常（可观测性）

**验收**：模拟宿主擅自传 `stage_confirmed=true` / `approver="user"` 而不带回执，
工具拒绝执行并给出结构化错误；现有合法调用路径行为不变。

**已落地**（2026-10-28）：宿主声明了 elicitation 时，`stage_confirmed`、`user_confirmed`、`waiver_user_confirmed` 只有本次 elicit 的继续回执才算数，否则返回 `Forbidden`（「这次确认没有 elicitation 回执」），门禁不清、处方不批。没声明时这三个参数仍走约定通道。高危项遇到 `approver="host_agent"` 直接拒绝，降级后再批其余的路径还在。`stage_confirmed=true` 且门禁为空时打一条警告：`stage_confirmed 为真，但当前没有待确认的门禁`。

#### 任务 1.3（可选，收益递减时先跳过）：工具语义收敛

把散落的布尔旋钮收敛成一个显式确认入口（例如 `hosp_advance(case_id, intent=...)`）。
**有破坏性**，建议等阶段 1.1/1.2 跑稳、且确实观察到误用后再做。

### 阶段 2 · 线索准入（模型结论如何进入处方）

**目标**：立起"模型说的话怎么变成可执行处方"这条规则。

**先澄清范围**：本阶段**不管**"源码送进模型"这一段（去程）——把源码给模型看是所有 AI
代码扫描的常态，不限制、也无需限制。本阶段管的是**回程**：模型产出的结论回到医院后，
够不够格变成处方项。

**为什么必须管**：code-hospital 与普通 AI 扫描工具的根本差别，在于结论的去向不同——
普通工具的输出是**建议给人看**，污染止于报告；本项目的输出是**处方给机器执行**，
`hosp_dispense` 会真的改代码。同一条被污染或幻觉出来的发现，在别处是信息噪声，
在这里是真实的代码改动。验证过自动修复是本项目主打能力，所以准入要比"给人看一眼"严一格。

#### 任务 2.1：线索准入规则

> 现有 `safety/sanitize.py` 净化的是**结论文本**里的可疑内容；本任务定的是**结论的准入资格**。
> 两者都在回程，不重叠。

规则（建议写成 `safety/admission.py`）：

- [x] 模型产出的结论**只能作为"待核实线索"**，不得直接写入结论性表述
- [x] 必须能落到 `file:line` 才准入方；落不到具体位置的一律丢弃并记录
      —— 与注入无关，是**可操作性**：处方项需要 `target_file` + 行范围才能施治
- [x] 模型说"这里没问题"**不得**写成"检查通过"——未核实 ≠ 通过
      —— 本项目已有同款纪律（roadmap E0「未交卷不能写成已分析」、覆盖账「没查的不能写成正常」），
      本条只是把它延伸到 LLM 结论
- [x] 模型结论在报告中单独分区，标题明示"待核实"，不混入仪器发现

**已落地**（2026-10-28）：`safety/admission.py` 按 `report` / `auto_advance` / `dispense` 三路给开关。默认只读报告只分区；自动档和施治打开全部四条。仓库根目录 `code-hospital.yaml` 的 `admission` 可以按路改这四项布尔值。自动档里宿主写「没有」并通读后，说明仍以「宿主已通读」开头，并接上「尚未核实，不能写成检查通过。」宿主诊断在严格档改成待核实措辞，不进入处方；落不到文件和行号的记入 `admission_drops`。施治若仍拿到这种药味，记一条护理日志后跳过，不改代码。

**严格度分级**（不要按最坏情况一刀切）：

| 链路 | 严格度 | 理由 |
|---|---|---|
| 只读链路（P0 PR 门诊，只出报告） | 松：只保留"报告分区标注" | 人最终会读报告，坏结论止于信息 |
| 自动档 `auto_advance` | 严：全部四条 | 无人在环，坏结论直接落到代码 |
| 常规施治链路（`hosp_dispense`） | 严：全部四条 | 结论驱动真实改码 |

建议实现为按链路可配置的开关，而不是写死的常量。

#### 任务 2.2：预算闸门

- [x] `catalog` 或环境变量增加 `max_llm_calls` / token 上限
- [x] 超限降级为仪器-only，并在覆盖账写明"本次因预算上限未做模型分析"
- [x] `hosp_treat` 自动档遵守同一闸门

**验收**：构造一个含大量发现的全仓体检，触发上限后流程不中断、覆盖账有明确记录。

**已落地**（2026-10-28）：上限写在环境变量 `CODE_HOSPITAL_MAX_LLM_CALLS`、`CODE_HOSPITAL_MAX_LLM_TOKENS`，或仓库 `code-hospital.yaml` 的 `catalog.budget`。环境变量优先。没配置就不限制。一次仪器发现算一次调用，四个字符估算一个 token。超限后检验照常留下仪器发现，覆盖账 `budget.degraded` 为真，并写上「本次因预算上限未做模型分析」。诊断不再标成宿主增强解读。需要模型补丁的药味改成人工处理。`hosp_treat` 走同一条检验，所以同一闸门生效。

### 阶段 3 · 执行方运行时与双向编排（治 R4 / R5）

> 本阶段部分内容超出当前阶段范围（见 C2）。架构预留做到，实现可以推迟。

#### 任务 3.1：执行方运行时

- [x] `executor=external` 从"登记 PATH"升级为"真正可跑"：
      白名单 + 不经 shell + 环境变量裁剪（已有）+ 超时 + 资源上限
- [x] 进程级沙箱作为**可选增强**（Linux namespace / Windows Job Object），默认关闭
- [x] 产物进覆盖账，缺产物写"外聘仪器未到岗"，不写成没问题

**已落地**（2026-10-28）：用户名册里 `engine: external` 的仪器按命令名在 PATH 上解析，参数不能带 shell 元字符，进程不经 shell，环境走验收命令那份裁剪。超时沿用检验的 `timeout_ms`（至少 1 秒），输出只留前 64KB。名册写了 `sandbox: true` 也不做进程隔离，覆盖记录里的 `sandbox` 仍是 false，并写明这次没有隔离。跑出的 JSON 发现只收就诊范围内的文件，`concluded_by` 写成 `external`，记在覆盖账 `external`。命令不在、超时、或没有可解析产物时写「外聘仪器未到岗」或「没有交产物，不能写成没问题」，不写检查通过。

#### 任务 3.2：架构预留（只做接口，不换实现）

按 C2"先个人后团队"，现在只抽接口：

- [x] 同仓互斥锁抽成 `Lock` 接口，默认实现仍是进程内锁
- [x] `hosp_treat` 的循环抽成可替换 `Driver`，默认实现仍是同步 12 步
- [x] 目标：阶段二真正换实现时，五个科室的代码一行不动

**已落地**（2026-10-28）：`runtime/lock.py` 的 `CaseLock.claim` 是同仓互斥的唯一入口。默认 `InProcessLock` 仍是查活跃病例：没有就放过，有且未 `force` 就 `Conflict`，`force` 就把旧病例转诊。不写文件锁。唯一索引仍留在病例表上。导诊台只调用 `case_lock.claim`。`runtime/driver.py` 的 `TreatDriver.run` 是自动档循环的唯一入口。默认 `SyncDriver` 仍是同步 12 步，科室顺序与原来一致。`hosp_treat` 只检查负超时，然后调用 `driver.run`。检验、坐诊、处方、药房、出院没有改。以后换锁或换编排，改这两个默认实例即可。

#### 任务 3.3：双向编排与疗效闭环

- [x] 医院兼作 MCP Client，调用 `java-code-review-mcp` 等外聘仪器，产物进覆盖账
- [x] 交卷契约结构化：schema + 校验 + 计入覆盖账（把任务单从纯文本升级为契约）
- [x] 疗效闭环：出院 diff → 后续复扫 → 复发率统计 → 沉淀评测集

**已落地**（2026-10-28，第三项）：出院把已消除的仪器发现按 `content_key` 写入 `.hospital/eval/set.json`，同一病例只留最新一份。下次检验拿这份评测集对照。有样本时覆盖账写 `recurrence`，限制项写消除了多少条、又出现多少条、复发率。没有样本，或样本里没有可对照的仪器发现，不算复发率。宿主交卷不进入这本账。这本账回答的是本仓库出院后仪器发现有没有再出现，不给药物排序，也不代替外部榜单的召回分。

**已落地**（2026-10-28，第二项）：宿主 LLM 的任务单带交卷契约 v1。文本行「文件:行: 说明」或「没有」加「已读：」仍然有效。对象写成 `{"issues":[{"file","line","message"}]}`，或 `{"clear":true,"read":[范围内每个文件]}`。路径必须在本次范围内，说明不能为空，问题和「没有」不能写在同一份里。没交、格式不对、或范围内还有文件没列入已读，都不能写成没有功能问题。覆盖账 `filing` 按事项记下 `open` / `invalid` / `held` / `filed` / `clear`。整份没通过时，单行解析成功也记成 `held`，不写入病历。

**已落地**（2026-10-28，只做第一项）：名册里 `engine: mcp` 的仪器由医院用 stdio 拉起。`command` 是 PATH 上的命令名，`tool` 是要调用的工具名，参数不能带 shell 元字符。环境用 MCP SDK 的默认裁剪。工具交回的文本按发现 JSON 解析，只收就诊范围内的文件，`concluded_by` 写成 `external`，记在覆盖账 `external`，`transport` 为 `mcp`。命令不在、超时或没有可解析产物时写「外聘仪器未到岗」或「没有交产物，不能写成没问题」。

**验收**：能通过一个评测集回答"这次改进到底提高了多少召回"，而不是靠感觉。

## 5. 能力线：召回与评测分数怎么提

> 本章与 [`code-hospital-roadmap.md`](./code-hospital-roadmap.md)（E0–E5）是**同一条线的两种视角**：
> roadmap 管"加哪些能力"，本章管"这些能力为什么现在上不去、先后顺序是什么"。
> 不重复 roadmap 的条目，只补它的**缺口**与**排序依据**。

**先给结论**：召回 ≈ 覆盖率 × 语义能力。架构不是瓶颈，但架构是语义能力的**前置**——
没有来源标记 / 准入规则 / 预算闸门，语义能力接不进来；硬接进来就会污染差分、烧穿成本。
所以第 4 章的架构线和本章的能力线**不是并行关系**，架构线阶段 0 与阶段 2 是能力线 C3 的前置。

### 5.1 为什么现在的分数低（三个根因，roadmap §1 已确认）

| 根因 | 证据 | 性质 |
|---|---|---|
| 单位不对齐 | 金标要"读懂这次改动在做什么"，尺子答"哪条规则响了"；行号重合 6/352 | **评测口径问题** |
| 覆盖不全 | 宿主交卷精确率 17/17，但大部分 PR 没读完 | 覆盖率问题 |
| 语义层没有尺子 | 功能对不对、SOLID、并发、N+1 只能靠模型 | 能力缺口 |

第一行是最容易被忽略的：金标是**描述性语义问题**，医院输出是**规则性发现**，
两者单位不同，重合率天然就低。**在口径对齐之前，你优化的可能是一个测错的东西。**

### 5.2 四块工作

#### C1 · 评测口径对齐（roadmap 未覆盖，建议最优先）

- [x] 定义"命中"的三级口径：**行级 / 函数级 / 语义等价**，分别统计
- [x] 人工标注 20–30 条金标与医院发现的对应关系，建立映射样本
- [x] 评测报告同时给出三种口径的分数，不再只报一个数字

**已落地**（2026-10-28，第一项）：`catalog/hits.py` 的 `score_hits` 分三档计。行级是同一文件的行号区间有重叠。函数级是同一文件且两边函数名相同；金标没有函数名就不进这一档。语义等价只认标注 `{gold_id, equivalent}`，行号重合不算语义命中。宿主交卷不参与行级和函数级。某一档没有分母时 `rate` 为空，写明不算分。Q6 定为三档都报，不单选。

**已落地**（2026-10-28，第二项）：`catalog/map_sample.py` 放了 24 条金标。材料是本机已有的 ReviewBench 裁判包，没有重跑，也没有新编评语。读过两边说明后，2 条标成同一缺陷，4 条对着医院发现但不是同一件事，18 条医院没有对应发现。另有 4 条医院发现没有金标，不进语义分母。`dataDir` 那条和前缀发现行号重叠，语义仍是 false；`k_max` 行号差一行，语义是 true。

**已落地**（2026-10-28，第三项）：`render_eval_report` 把行级、函数级、语义等价写进同一份评测报告，三档分开计，不合成一个分数。某一档没有分母就写不算分，不写 0。`sample_report` 用映射样本出这份报告：行级 2/24（前缀和 dataDir），函数级不算分，语义等价 2/24（前缀和 k_max）。没有金标的医院发现不进这三档。这不是全量重跑。

**产出**：第一次知道真实差距在哪——是没读到（覆盖率）、读到了没报（规则缺失）、
还是报了但单位不同（口径问题）。这三种情况对应的改进动作完全不同。

#### C2 · 覆盖率提升（= roadmap E0 收尾 + E3 延伸）

- [x] **E0 先收尾**：合入未交卷停住、全仓出院不得出现"没有功能问题"口径
- [x] 分轮交卷累加进同一份病历（E0 已设计）
- [x] 评测报告带覆盖率（E5 已要求）

**已落地**（2026-10-28，第三项）：`measure_coverage` 统计已读文件盖满范围的份数。`render_eval_report` 把这份覆盖率写在三档分数旁边，不并进行级、函数级或语义等价。没有范围账就写不算，不写 0。映射样本没有已读文件账，所以 `sample_report` 的覆盖率不算。某一份范围里还有文件没读，这份就不算盖满。

**已落地**（2026-10-28，第一项）：合入没有宿主交卷时，诊断返回 `pending_question(diff_filing)`，病例停在已检验，自动档遇到这份待确认就停。全仓出院（`scope_type=repo`）的正文不出现「没有功能问题」。未闭合链还在时写「功能结论停在未闭合清单，这次不出清」；链已闭合或没有链时写「这一节不给出清」。疗效判定仍只统计仪器发现，治愈不等于功能出清。

**已落地**（2026-10-28，第二项）：同一份病历可以分轮交卷。本轮写对的事项立刻入库，还没交的事项保持未闭合，诊断继续停在已检验。下一轮只追加新问题，相同的文件、行和说明不重复插入。已经入库的问题不会被后来的「没有」清掉。全部事项都是已交卷或已通读之后才写诊断书。

> 文档不一致已核对：roadmap §3 与 §6 都以现在的代码为准。合入未交卷、全仓出院口径、分轮交卷、评测报告上的覆盖率和处方草稿里的疗效后验都已落地。任务 1.3 仍跳过。

#### C3 · 语义能力接入（= E2 深化 + E4）—**召回的主杠杆**

内置尺子对语义金标帮助有限，roadmap §4 已明确"不用更多 YAML 规则去追 ReviewBench 的 350 条逻辑金标"。
真正的杠杆在这里：

- [x] E2 提示包深化：仓库自定义清单、清单项与发现的双向关联
- [x] E4 外聘仪器产物进病历（**依赖架构 3.1** 让 `external` 真能跑）
- [x] 语义结论标 `concluded_by=host_llm`，走准入规则（**依赖架构 0.1 + 2.1**）
- [x] 预算闸门（**依赖架构 2.2**）

**已落地**（2026-10-28，第一项）：仓库自定义清单仍用 `catalog.checks` 的 `items`、`packs`、`pack_dirs`，`group: checklist` 替换内置包。这次补上双向关联：发现记下 `check_id`，覆盖账 `filing.links` 从清单项指回发现，也从发现指回清单项。同一条问题可以挂在多条清单上。诊断书的合入交卷段写明「清单与发现」。外聘产物进病历、准入和预算闸门还没在这一项里做。

**已落地**（2026-10-28，第二项）：外聘进程和 stdio MCP 交来的 JSON findings、SARIF、`文件:行: 说明` 都收进病历，来源标 `external`。范围内没有命中写「外聘仪器已到岗，范围内没有命中」。空白或认不出的输出仍是「没有交产物，不能写成没问题」。命令不在 PATH 上仍写「外聘仪器未到岗」。这一项没有跑 `aigate-dgp`。准入和预算闸门还没做。

**已落地**（2026-10-28，第三项）：宿主交卷单独成簇，诊断标 `host_llm`，不再和同规则的仪器发现合成一条 `code` 诊断。自动档把这些诊断改成待核实措辞；落不到文件和行号的不进诊断。覆盖账 `admission` 记下链路和条数。自动档和施治仍不把这些线索写入处方。预算闸门还没在这一项里做。

**已落地**（2026-10-28，第四项）：超限后检查事项里待交的宿主 LLM 改为「因预算未做」，合入门诊不再把这份交卷写入病历。仪器发现仍在，诊断可以继续。覆盖账仍写「本次因预算上限未做模型分析」。需要模型补丁的药味仍改为人工处理。

**已落地**（2026-10-28，C4）：出院仍把消除的仪器发现写入 `.hospital/eval/set.json`，并记下这次范围和已读文件。清单每一项都是已通读时，已读文件等于这次范围。复发率只统计这些盖满的样本。没盖满的样本留在集里，不进分母，也不写成 0。没有样本时仍不算复发率。分数旁的覆盖率沿用 C2 第三项，评测报告仍把覆盖率写在三档外面。处方草稿的疗效后验见路线图 E5，已写入草稿说明，不改顺序。

#### C4 · 疗效闭环（= E5）

- [x] 出院样本累积；评测只统计"已读文件盖满范围"的病例
- [x] 分数旁必写覆盖率

### 5.4 见效预期（诚实版）

| 做完什么 | 分数会怎么变 | 确定性 |
|---|---|---|
| C1 评测口径 | **可能不升反降**（口径变严），但第一次知道真实差距 | 高 |
| C2 覆盖率 | 覆盖率上升，召回随之上升 | 较高 |
| C3 语义接入 | 语义召回上升，**幅度不确定**，取决于模型与清单质量 | 低 |
| 架构线（第 4 章） | **分数基本不变**，但打开 C3 的通道 | — |

C1 那一行要提前有心理准备：把口径校准之后分数大概率先难看，这是正常的，不是做错了。

## 6. 推进建议

### 6.1 优先级（架构线）

| 顺序 | 任务 | 治什么 | 破坏性 | 建议 |
|---|---|---|---|---|
| 1 | 0.1 来源标记 | 地基 | 低（加列） | **立即做** |
| 2 | 0.2 能力探测 | 可观测性 | 低 | 立即做 |
| 3 | 1.1 elicitation | R1 | 中 | 做，保留降级 |
| 4 | 1.2 服务端强校验 | R1 | 低 | **立即做**，性价比最高 |
| 5 | 2.1 线索准入 | 回程准入 | 中 | 让模型结论驱动改码**之前**必须做；只读链路可只取"报告分区" |
| 6 | 2.2 预算闸门 | 成本 | 低 | 与 2.1 同期 |
| 7 | 3.1 执行方运行时 | R4 | 中 | 可延后 |
| 8 | 3.2 架构预留 | R3 | 低 | 随手做，成本极低 |
| 9 | 3.3 双向编排 | R4/R5 | 高 | 最后 |

### 6.2 能力线的排期

能力线**不能与架构线完全并行**（见 §5.3 依赖矩阵），建议这样排：

| 顺序 | 任务 | 前提 |
|---|---|---|
| 1 | **C1 评测口径对齐** | 无，可立即开始；且应最早做，否则后面无法衡量 |
| 2 | C2 覆盖率（E0 收尾） | 无 |
| 3 | 架构线 0.1 / 0.2 / 1.2 | 无 |
| 4 | 架构线 2.1 / 2.2 | 0.1 |
| 5 | **C3 语义接入** | 0.1 + 2.1 + 2.2 |
| 6 | C4 疗效闭环 / 架构线 3.x | 以上 |

**如果只做一件能力层的事，做 C1。** 它不直接提分，但没有它，你无法判断后面每一步到底有没有提分。

### 6.3 每个阶段的完成判据

一个阶段算完成，必须同时满足：

1. 该阶段对应的风险条目在验收场景中**不再复现**
2. 现有 P0 链路（挂号→检验→诊断→开方→施治→出院）**行为不变**
3. 覆盖账/报告中能**看到**该次运行用了哪条路径（协议级还是约定级、仪器还是模型）
